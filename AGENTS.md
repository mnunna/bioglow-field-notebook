# BioGlow repository guidance

This file applies to the entire repository. Keep it concise and update it when the development workflow or product constraints change.

## Product principles

- BioGlow is an offline-first field notebook for ecologists. Core capture, browsing, and export must work without an account or network connection.
- Field observations stay on the device unless the user explicitly exports or shares them.
- Preserve camera, location, photo-library, and microphone permission explanations when changing related features.
- Design for use outdoors and with wet hands. Rain / Glove Mode and accessible tap targets are product requirements, not decoration.
- Support both iOS and Android unless a task is explicitly platform-specific. Camera, GPS, audio, sharing, and filesystem changes require device-level consideration.

## Repository layout and native projects

- `App.tsx` owns navigation and top-level app state.
- `src/screens/` contains product screens; `src/components/` contains shared UI.
- `src/storage.ts` owns persisted field entries and CSV generation.
- `src/templates.ts` and `src/types.ts` define the field-note model.
- `app.json` is the source of truth for Expo identity, permissions, plugins, and native configuration.
- `plugins/` contains persistent Expo config plugins needed by generated native projects.
- `ios/` and `android/` are generated by Expo and intentionally ignored. Do not treat manual edits inside them as permanent fixes. Put durable native changes in `app.json` or an Expo config plugin.
- Preserve the existing iOS deployment-target, path-with-spaces, script-sandboxing, and scene-lifecycle plugins unless the replacement is verified with the installed Xcode/iOS toolchain.

## Commands

Run commands from the repository root:

```bash
npm install
npm run typecheck
npm start
npm run ios:device
```

Use `npm run typecheck` as the minimum automated check. Features involving camera, GPS, audio, sharing, permissions, filesystem behavior, or native configuration should also be exercised on a physical iPhone before being called complete.

## Working conventions

- Inspect `git status` before editing and preserve unrelated user changes.
- Keep changes focused on one outcome. Avoid drive-by refactors while implementing a feature or fix.
- Prefer the existing dependency set. Explain and verify any new dependency, especially one that adds native code.
- Keep TypeScript types explicit at storage, navigation, and native-module boundaries.
- Never commit secrets, signing material, provisioning profiles, generated native folders, build output, or local environment files.
- Update `README.md` when setup or user-visible behavior changes.
- `ROADMAP.md` is the planning source of truth. `src/screens/IdeasScreen.tsx` is the concise, user-facing snapshot; synchronize it deliberately when roadmap changes are ready to appear in the app.
- Explore uncertain ideas in `docs/ideas/` before writing implementation code. Promote an idea to the roadmap only after its problem, intended outcome, constraints, and smallest useful version are clear.

## Branching strategy

- `main` should remain buildable and suitable for installing on a test device.
- Normal development happens on a short-lived branch created from an up-to-date `main`.
- Codex-created branches use `codex/<short-kebab-case-topic>`, for example `codex/offline-backup` or `codex/improve-photo-capture`.
- Keep one coherent outcome per branch. Do not use a long-lived `develop` branch.
- Make small, logical commits. Do not mix unrelated cleanup, idea exploration, and feature implementation in the same commit.
- Before merging, review the diff, run `npm run typecheck`, and perform the relevant device checks. Record any check that could not be run.
- Prefer a pull request and squash merge into `main`, then delete the feature branch. Direct commits to `main` should be exceptional and explicitly requested.
- If the working tree already contains unrelated changes, do not reset, discard, or overwrite them. Continue only when the work can be isolated safely; otherwise pause and ask whether to commit the baseline or use a separate worktree.

## Definition of done

A change is done when the requested behavior is implemented, TypeScript passes, relevant device behavior is verified, documentation is current, no secrets or generated native files are included, and the final diff contains only intended changes.
